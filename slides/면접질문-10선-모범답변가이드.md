# Friday 발표 — 면접 질문 10선 & 모범 답변 가이드

> 10년차 AI 면접관 관점의 날카로운 질문 + 각 질문에 대한 **방어 전략**.
> 모범 답변은 (a) 사실 기반으로 솔직하게 인정할 것은 인정하고, (b) 설계 의도를 명확히 하고, (c) 한계는 *후속 계획*으로 전환하는 3단 구조를 따른다.
> 면접 답변의 황금률: **"모릅니다"보다 "현재는 X까지 했고, Y는 인지된 한계이며, Z로 해결할 계획입니다"**.

## 1. Self-RAG의 환각 검사 — "심판도 LLM"이라는 모순

**❓ 질문**
환각을 판정하는 grader도 LLM입니다. 생성기가 환각하면 판정기도 통과시킬 수 있는데, 이 self-grading이 환각을 잡는다는 걸 무엇으로 증명했습니까? 재시도 후에도 환각이면 종료 조건과 fallback은?

**✅ 모범 답변**
- **핵심 반박**: "생성기와 판정기는 *입력이 다릅니다*. 판정기는 '답변 + 출처 문서'를 함께 받아 **문서에 근거가 있는가(grounding)**만 봅니다. 자유 생성보다 훨씬 제약된 판별 태스크라 환각 확률이 구조적으로 낮습니다."
- **재시도 설계 (ADR-0053)**: "재시도는 동일 입력 재호출이 아닙니다. 재진입 시 grounding 교정 절(`REGENERATE_GROUNDING_NOTICE`)을 프롬프트에 덧붙여 *입력 자체를 바꿉니다* — '문서 근거를 강제하고, 없으면 모른다고 답하라'. 같은 실수를 반복할 확률을 낮춘 것."
- **종료 조건**: "`retry_count` 임계값으로 무한루프를 차단하고(`edges.py` 라우팅), 한도 초과 시 추측 답변 대신 **'근거 부족으로 확정 답변 불가'로 안전하게 종료**합니다. fail-safe는 '모른다'쪽."
- **솔직한 한계**: "self-grading의 절대 신뢰성은 LLM-as-judge 한계를 공유합니다. 그래서 출처 인용 *의무화*를 2차 방어선으로 둬서, 사용자가 직접 근거를 검증할 수 있게 했습니다."

**🚫 피할 답변**: "GPT가 똑똑해서 잘 잡습니다" (측정 없는 신뢰는 감점)

## 2. 권한 pre-filter와 검색 recall의 trade-off

**❓ 질문**
권한으로 후보군을 먼저 좁히면 볼 수 있는 자료의 recall이 떨어지지 않습니까? path 정확매칭이면 폴더 경계 답변은 누락될 텐데, 정량 측정했습니까?

**✅ 모범 답변**
- **설계 의도 (ADR-0015)**: "이건 trade-off가 아니라 *의도된 보안 경계*입니다. `ListObjects(can_read, folder)`로 읽을 수 있는 폴더 목록을 받고, 그 폴더에 **정확 매칭(`path = ANY`)**되는 청크만 검색합니다. prefix 확장을 일부러 안 합니다 — private 하위 폴더 누수를 막기 위해."
- **recall 관점 재정의**: "권한 밖 문서는 *애초에 답변 대상이 아닙니다*. 그러니 그것을 못 가져온 건 recall 손실이 아니라 정상 동작입니다. 측정해야 할 건 '**권한 있는 자료 안에서의** recall'이고, 이건 pre-filter 후의 top-k 안에서 평가됩니다."
- **측정 현황 (솔직)**: "검색 적중률(retrieval hit rate)을 eval 하니스 지표로 보유합니다(슬라이드 10). 다만 '권한 경계가 recall에 주는 영향'을 *분리한* 별도 실험은 아직 안 했습니다 — 후속 과제로 인지하고 있습니다."
- **반격 카드**: "오히려 pre-filter는 검색 노이즈를 줄여 **precision을 올립니다**. 권한 밖 유사 문서가 top-k를 차지하던 걸 제거하니까요."

## 3. 캐시 일관성 — "즉시 반영"의 실제 윈도우 ⭐약한 고리

**❓ 질문**
"즉시 반영"과 "TTL 캐시"는 충돌합니다. revoke 직후 stale 캐시로 권한 밖 문서가 검색되는 윈도우는? 집합 subject 무효화 실패 시 fail-open입니까 fail-closed입니까?

**✅ 모범 답변**
- **즉시 무효화 설계 (ADR-0054)**: "TTL 만료를 기다리지 않습니다. grant/revoke 시점에 **능동적으로 캐시를 무효화**합니다. 개별 user subject는 본인 것만, 집합 subject(`X#member` — department holder, role super_reader 등)는 TTU 파급으로 **멤버 전원 것을 무효화**합니다."
- **핵심 — fail-closed 명시**: "질문의 핵심을 정확히 짚으셨습니다. **멤버 열거나 무효화에 실패하면 캐시 *전체*를 flush합니다(fail-closed).** 즉 의심스러우면 캐시를 버리고 OpenFGA에 직접 묻습니다 — 느려질지언정 권한 밖 노출은 막습니다."
- **윈도우 정직하게**: "이론적 stale 윈도우는 '무효화 호출과 다음 검색 사이'로, 단일 트랜잭션 수준입니다. 분산 복제 환경이라면 복제 지연 윈도우가 추가되는데, 현재는 PostgreSQL 단일 인스턴스라 해당 없습니다. 멀티 리전 확장 시엔 이 부분 재설계가 필요합니다."
- **마무리**: "보안 캐시의 제1원칙은 '**틀리면 막는 쪽으로 틀려라**'이고, 그걸 fail-closed flush로 구현했습니다."

## 4. 프롬프트 인젝션 — 문서 자체가 공격자라면

**❓ 질문**
검색돼 들어온 문서 본문에 인젝션이 심겨 있다면? SQL 에이전트가 인젝션으로 다른 테이블을 조회하는 SQL을 생성하면? 테이블 viewer 게이트가 LLM 출력 *앞*입니까 *뒤*입니까?

**✅ 모범 답변**
- **핵심 — 게이트는 LLM *뒤*, 실행 *앞* (ADR-0050·0051)**: "결정적 포인트입니다. LLM이 어떤 SQL을 생성하든, **실행 직전에** `table:employees`/`table:sales`의 `viewer` relation으로 하드 게이트를 겁니다. 인젝션으로 다른 테이블을 노린 SQL이 생성돼도, **접근권 미보유 시 실행 전 DENY**됩니다. LLM의 출력을 신뢰하지 않는 구조입니다."
- **이중 게이트**: "테이블 접근권(`viewer`)과 위험도 게이트(`capability:sql`, ADR-0047)가 **AND** 조건입니다. 둘 다 통과해야 실행됩니다."
- **권한은 LLM 무관**: "문서 검색 권한도 마찬가지입니다. pre-filter는 *사용자 신원* 기반이라 문서 본문의 인젝션 문구가 권한 범위를 바꿀 수 없습니다. '전체 매출 보여줘'라고 문서가 외쳐도, 그 사용자에게 sales 폴더 권한이 없으면 검색 자체가 안 됩니다."
- **쓰기 추가 방어 (ADR-0034)**: "쓰기는 별도 계정(`sql_tool_rw`)에 WHERE 필수 가드까지. 읽기 계정으론 쓰기가 물리적으로 불가."
- **솔직한 한계**: "다만 *답변 텍스트 내 인젝션 전파*(검색된 문서가 사용자에게 거짓 지시를 하는 social engineering)는 여전히 LLM 일반 한계입니다. 출처 인용으로 사용자가 원문을 검증하게 한 게 현재 방어."

**🚫 피할 답변**: 게이트가 LLM "앞"이라고 답하면 인젝션에 무력 — 반드시 "실행 직전"임을 강조.

## 5. SQL 쓰기 HITL — 승인이 rubber-stamp가 되는 문제

**❓ 질문**
승인자가 LLM 생성 `UPDATE ... WHERE`의 영향 범위를 판단할 수 있습니까? `WHERE 1=1`이면 전체 테이블을 칩니다. UI가 영향 행 수를 보여줍니까?

**✅ 모범 답변**
- **현재 설계**: "HITL 승인 시 **실행될 SQL 원문과 작성 사유**를 사용자에게 제시하고(`interrupt()`, ADR-0042), 명시적 승인을 받아야 실행됩니다. 사유 기록은 감사 로그에 남습니다(ADR-0052)."
- **솔직한 인정 + 개선안**: "영향 행 수 dry-run 프리뷰는 **현재 미구현이고, 타당한 지적입니다.** `EXPLAIN`이나 `SELECT count(*) WHERE <동일조건>`을 승인 화면에 함께 띄우면 rubber-stamp를 실질 검토로 바꿀 수 있습니다. 후속 과제로 명확히 인지합니다."
- **현재의 보완 장치**: "다만 무방비는 아닙니다 — (1) WHERE 절 *필수* 가드로 무조건부 UPDATE/DELETE를 막고, (2) 읽기/쓰기 계정 분리로 권한 자체를 제한하고, (3) 모든 쓰기가 감사 로그에 남아 사후 추적·롤백 근거가 됩니다."
- **마무리**: "즉 '예방(WHERE 가드)+통제(HITL)+탐지(감사)'의 3중 구조 중 *예방의 정밀도*를 행 수 프리뷰로 높이는 게 다음 스텝입니다."

## 6. 평가 체계의 공백 — "정량 목표치가 없다" ⭐약한 고리

**❓ 질문**
회귀 채점은 보유했지만 정량 목표치는 *향후 계획*입니다. 목표 없는 채점은 "충분히 좋은가"를 못 답합니다. 배포 가능한 품질이라는 근거는? 환각률·false allow 현재 수치는?

**✅ 모범 답변**
- **프레이밍 전환**: "맞습니다. 다만 구분이 필요합니다 — 현재 보유한 건 **상대적 회귀 게이트**이고, 미보유한 건 **절대적 합격선**입니다. 둘은 용도가 다릅니다."
- **있는 것 (사실)**: "회귀 게이트는 작동 중입니다. 실제로 데모 성능 최적화에서 grade를 LLM→cosine 휴리스틱으로 바꿀 때, **eval 점수 0.875→0.896 회귀 게이트를 통과**시켜 품질 하락 없음을 확인하고 머지했습니다(ADR-0056). 즉 '변경이 품질을 떨어뜨렸는가'는 정량으로 막고 있습니다."
- **없는 것 (솔직)**: "절대 목표치(예: '환각률 <2%, false allow =0')는 아직 수립 못 했습니다. 슬라이드 11에 *향후 계획*으로 명시한 이유입니다. **3주 프로젝트에서 측정 *체계*를 먼저 세우고 목표 *수치*는 다음 단계로 둔 우선순위 결정**이었습니다."
- **배포 가능성 재정의**: "그래서 저는 이걸 '프로덕션 ready'가 아니라 '**프로덕션을 향한 검증된 프로토타입**'으로 정의합니다(슬라이드 11도 그렇게 표현). 배포 전 게이트는 정량 목표 수립 → 그 목표 기준 평가가 선행돼야 한다고 봅니다."
- **반격 카드**: "오히려 측정 *없이* 'GPT 쓰니 잘 됩니다'로 배포하는 게 더 위험합니다. 저는 측정 인프라를 먼저 깔았습니다."

## 7. 권한 정확도의 비대칭성 — false allow는 단 1건도 안 된다

**❓ 질문**
72건+ 테스트가 false deny와 false allow를 구분합니까? 조합 폭발을 예제 나열로 어떻게 보장합니까 — property-based가 아니라?

**✅ 모범 답변**
- **비대칭 인정**: "정확한 지적입니다. false deny는 불편, false allow는 사고 — 이 비대칭에 동의합니다."
- **현재 커버리지**: "72건은 부서·개인·역할 holder별 허용/차단 케이스를 모두 포함합니다(ADR-0051 permission 통일 모델). 특히 **'권한 없는 사용자가 권한 밖 폴더를 검색 → 차단'** 시나리오는 데모 라이브 검증까지 마쳤습니다(④⑤⑦ 장면)."
- **구조적 방어 (예제 너머)**: "예제 나열의 한계를 모델 설계로 보완합니다 — pre-filter는 '허용 목록(allowlist)' 방식이라 **기본이 deny**입니다. 명시적으로 부여된 폴더만 통과하므로, 새 문서·새 부서는 *자동으로 차단*에서 시작합니다. false allow가 나오려면 *적극적 오부여*가 있어야 하고, 그건 grant 경로 테스트로 좁혀집니다."
- **솔직한 한계 + 개선안**: "**property-based test는 미도입이고 타당한 다음 스텝입니다.** '임의의 사용자×임의의 폴더 조합에서, OpenFGA check 결과와 실제 검색 가능 문서 집합이 일치한다'는 invariant를 생성 테스트로 돌리면 조합 폭발을 커버할 수 있습니다. 후속 과제로 기록하겠습니다."
- **fail-closed 연결**: "그리고 캐시 실패 시 fail-closed(3번 답변)라 시스템 *오류*로 인한 false allow는 구조적으로 막혀 있습니다."

## 8. 비용·지연의 현실 — 한 질문에 LLM이 몇 번 도나

**❓ 질문**
한 질문에 라우팅→rewrite→grading→생성→환각검사가 모두 LLM이면 p95 지연·비용은? "검색 시간 0"과 충돌 아닙니까?

**✅ 모범 답변**
- **수치 인지 (사실)**: "정확히 측정했습니다. **데모 시간의 ~99%가 OpenAI LLM 왕복**이라는 게 벤치마크 결론이었습니다(`demo_bench.py`). 인프라가 아니라 LLM이 병목이라는 걸 *데이터로* 알고 있습니다."
- **실제 최적화 실적 (ADR-0055·0056)**: "그래서 호출 수와 경로를 줄였습니다 — (1) **router∥rewrite 병렬화**로 장면당 1.83×, (2) **FGA 클라이언트 재사용**으로 7.7×, (3) 콜드스타트 워밍업으로 첫 요청 8초→1.1초, (4) 결정적으로 **grade 단계를 LLM→cosine 임계 휴리스틱**으로 교체해 697ms→0.008ms(장면당 ~0.7초 절감). 이 변경은 eval 회귀 게이트 0.896을 통과해 품질 손실 없음을 확인했습니다."
- **"검색 시간 0" 방어**: "그 메시지는 *사람이 문서를 찾아 헤매는 시간*(수 분~수십 분)이 0이 된다는 가치 제안이지, LLM latency가 0이라는 게 아닙니다. 수 초의 응답 대 수십 분의 수작업 검색 — 그 대비에서 여전히 압도적입니다. 게다가 스트리밍으로 첫 토큰까지의 체감 지연을 줄였습니다."
- **비용**: "호출당 비용은 gpt-4.1-mini 기준으로 낮고, grade 휴리스틱화로 호출 *수*도 줄였습니다. 1,000명 규모 정밀 추산은 부하 테스트가 선행돼야 해 *현재 미수행*임을 인정하며, 모델 교체 가능 구조라 비용/성능 튜닝 여지를 남겨뒀습니다(슬라이드 7)."

## 9. 엔터프라이즈 통합 — OpenFGA가 source of truth라는 위험

**❓ 질문**
실제 회사는 AD/LDAP/SSO/HR이 source of truth입니다. OpenFGA와 어긋나면(퇴사자 잔존 등) 누가 이깁니까? "구글이 쓰는 권한 모델"은 과장 아닙니까?

**✅ 모범 답변**
- **현재 범위 솔직히**: "현 프로젝트에서 OpenFGA가 source of truth인 건 *이 시스템 경계 안* 이야기입니다. `config/users.yaml`은 부트스트랩 시드일 뿐이고(멱등·일방향, `seed_fga.py`), 운영 멤버십은 OpenFGA에서 관리합니다. 실제 엔터프라이즈에선 말씀대로 **HR/IdP가 상위 source of truth**가 돼야 합니다."
- **통합 아키텍처 제시**: "프로덕션 통합은 **OpenFGA를 IdP의 *투영(projection)*으로 두는 구조**가 정답입니다 — SCIM/LDAP 동기화로 HR→OpenFGA 단방향 sync, 퇴사 시 IdP deprovision이 OpenFGA 튜플 제거로 파급. 충돌 시 **항상 IdP가 이깁니다.** 이건 Zanzibar류 시스템의 표준 배치 패턴입니다."
- **"구글 모델" 표현 방어**: "그 표현은 **권한 *모델*(Zanzibar 관계 기반 ReBAC)이 동일 계열**이라는 뜻이지, 구글 스케일 운영을 했다는 주장이 아닙니다. 폴더·테이블·개인 위임을 관계 튜플로 표현하는 그 방식은 실제로 동일합니다. 다만 발표 청중에 따라 '구글이 사내 권한에 쓰는 것과 *같은 계열의* 모델'로 더 정확히 표현하겠습니다."
- **마무리**: "통합 비용을 숨기지 않습니다 — IdP 연동은 프로덕션화의 명시적 다음 관문이고, 현재는 그 *권한 엔진*을 검증한 단계입니다."

## 10. 멀티턴 대화에 남는 민감정보 — checkpointer의 사각지대

**❓ 질문**
권한은 질문 시점에 막지만, 이전 턴 답변의 민감정보는 히스토리에 남습니다. 권한 회수 후 같은 대화를 이으면 박제된 매출 수치가 다시 컨텍스트로 들어가지 않습니까? 회수가 과거 대화에 소급됩니까?

**✅ 모범 답변**
- **날카로움 인정**: "권한의 *시간축*을 정확히 짚으셨습니다. 검색 권한은 *질문 시점*에 평가되지만, 대화 상태(`AgentState`, MemorySaver)는 과거 답변을 보존합니다. **현재 권한 회수는 과거 checkpoint에 소급되지 않습니다.** 인지된 한계입니다."
- **현재 완화 요소**: "다만 영향은 제한적입니다 — (1) checkpoint는 **세션/스레드 단위로 격리**돼 타인이 그 히스토리에 접근할 순 없습니다(자기 대화 안에서만 잔존), (2) 회수 *이후의 새 검색*은 즉시 차단됩니다(fail-closed 캐시). 즉 '새로운 권한 밖 정보 획득'은 막히고, 남는 건 '이미 본 정보의 잔상'입니다."
- **개선안 제시**: "정공법은 **(a) 민감 답변에 권한 컨텍스트를 태깅**해두고, 다음 턴에서 히스토리를 LLM에 넣기 전 *현재 권한으로 재검증*해 무효화된 청크를 마스킹하는 것, 또는 **(b) 권한 회수 이벤트 시 해당 subject의 활성 thread checkpoint를 무효화/재작성**하는 것입니다. 후속 과제로 명확히 기록하겠습니다."
- **원칙 마무리**: "'한 번 정당하게 본 정보의 잔상'과 '회수 후 새 접근 차단'은 다른 문제이고, 후자는 막혀 있습니다. 전자(소급 삭제)는 GDPR 'right to be forgotten'급 요구로, 별도 설계 트랙입니다."

## 부록 — 답변 전반의 메타 전략

| 상황 | 전략 |
|---|---|
| 약점을 정확히 찔렸을 때 | **먼저 인정** → "정확한 지적입니다" → 설계 의도 → 후속 계획. 방어적 부인은 감점. |
| "측정했냐"는 질문 | 있으면 **수치로**(eval 0.896, 7.7×, 72건), 없으면 "측정 *체계*는 있고 *목표치*는 다음 단계" |
| "프로덕션 되냐" | "검증된 프로토타입"으로 정직하게 포지셔닝. 과대포장 금지. |
| 보안 질문 전반 | 키워드는 **fail-closed, allowlist(기본 deny), 다층 방어(예방+통제+탐지)** |
| 모르는 영역 | "현재 범위 밖이지만, 접근한다면 X 방향"으로 *사고 과정*을 보여주기 |

**3주 / 1인 프로젝트라는 제약을 무기로**: "한정된 시간에 *무엇을 먼저 검증할지* 우선순위를 정한 결정"으로 모든 미구현을 프레이밍할 것. 미구현 ≠ 무지, 미구현 = 의식적 스코프 결정.
