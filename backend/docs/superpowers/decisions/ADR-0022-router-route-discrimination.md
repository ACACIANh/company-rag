# ADR-0022: 라우터 doc_search↔tool_call 분류 정확도 개선

> **Status**: 🟢 적용완료   <!-- 🟢 적용완료 · 🔵 승인됨 · ⚪ 제안됨 · 🟡 보류 · 🟣 대체됨 · ⚫ 폐기 -->
> 구현 범위: Decision 1(데이터 원천 기준 재정의)·2(경계 few-shot)·4(doc_search 폴백)만 적용(feat/adr-0022-router-discrimination). **3(라우팅 정확도 eval 하니스)은 보류** — 아래 후속 참조.

**Date**: 2026-06-02
**Context**: `router_node`([app/graph/nodes/router.py](../../../app/graph/nodes/router.py))는 `ROUTER_PROMPT`([app/graph/prompts.py](../../../app/graph/prompts.py))로 질문을 `doc_search`(사내 문서 검색)와 `tool_call`(현재 NL→SQL 조회) 중 하나로 분기한다. 그런데 현재 프롬프트의 경계가 **동작 동사**(예약·조회·실행·전송)에 기대고 있고, 특히 "**조회**"가 `tool_call` 설명에 들어가 있어 "휴가 조회 정책"(문서)과 "내 연차 조회"(DB)가 같은 동사로 충돌해 오분류가 난다. 게다가 라우팅이 맞는지 **측정할 수단이 없어**(eval에 라우팅 지표 부재) 프롬프트를 고쳐도 개선 여부를 알 수 없다. 분류 기준을 무엇으로 둘지, 어떻게 검증할지 결정한다.

## Options

| 선택지 | 트레이드오프 |
|--------|------------|
| **(1) 기준을 데이터 원천으로 재정의** | "동작이면 tool_call"이 아니라 "`business.employees`/`business.sales` 테이블 값으로 답되면 tool_call, 문서 서술로 답하면 doc_search". 경계가 선명해지고 SQL 스키마(이미 `SQL_GENERATE_PROMPT`에 존재)와 일관. 프롬프트 수정만으로 저비용 |
| **(2) 경계 few-shot 주입** | 형식 예시뿐인 현재 프롬프트에 *판단* 대조쌍("연차 며칠까지 쌓여?"→doc / "내 연차 며칠 남았어?"→tool)을 추가. 가장 헷갈리는 구간을 직접 교정. 토큰 소폭 증가 |
| (3) 구조화 출력 + 신뢰도/근거 | 문자열 파싱 대신 reason·confidence를 함께 받아 디버깅·라벨링 용이, 낮은 신뢰도는 doc_search 폴백. 출력 스키마 변경·토큰 증가. 1·2 효과 확인 후로 미룸 |
| **(4) 라우팅 정확도 측정** | 라벨링 질문셋(질문→정답 route)으로 confusion matrix·정확도를 `tests/eval/runner.py`에 추가. 어느 방향 오분류가 많은지 드러나고 프롬프트 회귀 방지. 라벨링 초기 비용. **개선의 검증 토대** |
| (5) clarify 노드(모호 시 되묻기) | 양쪽으로 읽히는 질문을 찍지 않고 사용자에게 의도 확인. UX·정확도 이득이나 노드/엣지 추가(그래프 구조 변경). `interrupt` 기반이면 HITL 메커니즘 재사용([confirm.py](../../../app/graph/nodes/confirm.py))이나 목적(명확화)·위치(분기 전)가 `confirm_node`(승인·실행 직전)와 달라 별개 노드. **별도 ADR로 분리** |

## Decision

**선택: (1) 데이터 원천 기준 재정의 + (2) 경계 few-shot + (4) 라우팅 정확도 측정을 함께 채택한다.**

1. **`ROUTER_PROMPT` 기준 재정의**: route 선택지 설명을 동작 동사 나열에서 **데이터 원천**으로 바꾼다.
   - `doc_search`: 정책·규정·절차·가이드 등 **비정형 문서에 서술된** 내용.
   - `tool_call`: `business.employees`/`business.sales` **테이블의 특정 레코드·집계 값**으로 답하는 질문.
   - 판정 기준 문구를 "이 질문이 두 테이블의 값으로 답되는가?"로 명시. SQL 스키마를 라우터에도 노출해 `sql_generate_node`와 같은 인식 기반을 공유한다.
2. **경계 few-shot 추가**: 출력 형식 예시와 별개로, 오분류가 나는 대조쌍을 프롬프트에 넣는다. 최소 셋:
   - "연차는 며칠까지 쌓을 수 있어?" → `doc_search:none` (규정=문서)
   - "내 연차 며칠 남았어?" → `tool_call:none` (개인 값=DB)
   - "급여 인상 정책 알려줘" → `doc_search:none` / "영업팀이랑 개발팀 평균 급여 비교" → `tool_call:none`
3. **라우팅 정확도 eval**: `tests/eval/`에 라벨링된 질문셋(질문→정답 route, 경계 케이스 포함 30~50개)과 confusion matrix·정확도 산출을 추가한다. 프롬프트 변경마다 회귀를 확인하고(DoD 2번), 오분류 패턴이 곧 2번 few-shot의 소스가 된다.
4. **불확실 구간은 doc_search로 기운다**: 모호하면 `tool_call`을 억지로 고르기보다 폴백. `tool_call`은 SQL 게이트(ADR-0016~0018)·HITL이 걸려 비용/위험이 크고, doc_search 오작동은 "근거 없음" 답으로 끝나는 **비대칭 비용** 때문. 현재 파싱 실패 시 doc_search 폴백 방향과 일치하므로 기존 폴백은 유지한다.

## Rationale

- **실패 모드가 "동사 충돌"로 특정됨** → 처방은 동사 사전을 늘리는 게 아니라 분류 *축*을 바꾸는 것(데이터 원천). 이 코드베이스에서 tool_call의 실체는 NL→SQL이라 "테이블로 답되나"가 가장 정확한 판별식이고, 스키마가 이미 코드에 존재해 추가 비용이 거의 없다.
- **few-shot은 1번의 보강재**: 기준을 바꿔도 경계 케이스는 남으므로, 모델이 가장 헷갈리는 "정책 vs 내 수치" 대조를 직접 보여주는 게 효과적. 1·2는 프롬프트만 고치는 저비용·고효과라 묶어서 먼저 한다.
- **측정 없이는 개선을 모른다** → 4번이 1·2의 검증 토대. confusion matrix로 어느 방향 오분류가 많은지 보고 그 방향을 집중 교정하는 폐루프를 만든다. 메모리에 적힌 eval 하니스 부채와 같이 엮을 수 있다.
- **3·5는 의도적으로 보류**: 3(구조화 출력)은 1·2·4로 충분치 않을 때 도입할 다음 단계, 5(clarify)는 그래프 구조 변경이라 별도 ADR. 지금은 프롬프트+eval 수준의 최소 개입으로 효과를 먼저 확인한다(YAGNI).

## 미해결 / 후속

- **Decision 3) 라우팅 정확도 eval 하니스 — 보류**: 라벨링 질문셋·confusion matrix는 이번 구현에서 제외했다. 따라서 1·2·4의 분류 개선 효과는 아직 정량 검증되지 않았다(프롬프트 단위 테스트로 의도만 고정). 효과 측정이 필요해지면 `tests/eval/`에 별도로 추가한다.
- **(3) 구조화 출력/신뢰도** — 1·2·4 적용 후에도 경계 오분류가 남으면 reason·confidence 출력으로 확장 검토.
- **(5) clarify 노드** — 진짜 양의적 질문 비율이 eval에서 유의하게 관측되면 `interrupt` 기반 의도 명확화 노드를 **별도 ADR**로 설계. `confirm_node`와 합치지 않는다(승인 게이트 ≠ 의도 명확화).
- **tool_call의 도구 확장** — 향후 tool_call이 SQL 외 웹검색 등으로 늘면(에이전트화 과제) "테이블로 답되나" 판별식을 도구 목록 기반으로 일반화해야 한다.
