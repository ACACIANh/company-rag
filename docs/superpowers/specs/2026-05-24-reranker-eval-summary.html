Two-Stage Retrieval에서 Reranker가 순위 품질에 미치는 영향:
Listwise LLM Reranker 평가 보고서

Date: 2026-05-24 System: company-rag (LangGraph RAG, Phase 5) Baseline: NoRerank (dense retrieval, top_k=5) Treatment: LLMReranker (top_k=20 → 5, gpt-4o-mini listwise) Dataset: doc_search 경로 질문 10개

개요

현대 정보 검색(Information Retrieval) 시스템은 대규모 코퍼스에서 효율적으로 문서를 후보군으로 좁히는 1단계(Recall 중심)와, 소수 후보를 정밀 재정렬하는 2단계(Precision 중심)로 구성된 Two-Stage Retrieval 패러다임을 채택한다.

본 보고서는 company-rag 프로젝트에서 수행한 실험 결과를 바탕으로, Listwise LLM Reranker를 2단계로 추가했을 때 검색 품질이 어떻게 변화하는지를 Recall@k 및 MRR 지표로 분석한다.

배경: Two-Stage Retrieval과 Recall–Precision Tradeoff

2.1 구조 개요

Query │ ▼ ┌──────────────────────────────────────┐ │ Stage 1: Dense Retrieval │ │ (Bi-encoder / BM25) │ │ 목표: Recall ↑ (후보 k₁개 확보) │ │ 비용: O(1) per query (ANN search) │ └──────────────────┬───────────────────┘ │ top-k₁ candidates ▼ ┌──────────────────────────────────────┐ │ Stage 2: Reranker │ │ (Cross-encoder / LLM Listwise) │ │ 목표: Precision / MRR ↑ │ │ 비용: O(k₁) per query │ └──────────────────┬───────────────────┘ │ top-k₂ results (k₂ << k₁) ▼ 최종 응답 생성 (LLM)

2.2 왜 1단계만으로는 부족한가

Dense Retrieval(bi-encoder)은 쿼리와 문서를 각각 독립적으로 인코딩하기 때문에 쿼리-문서 상호작용(cross-attention)을 직접 모델링하지 못한다. 그 결과, 의미적으로 유사한 문서를 빠르게 후보군에 포함시키는 능력(Recall)은 높지만, 정확히 어떤 문서가 더 적합한지 순위를 매기는 능력(Precision at top-1, MRR)은 떨어지는 경향이 있다.

핵심 직관
1단계는 "정답 문서를 놓치지 않기" 위한 단계이고,
2단계는 "정답 문서를 가장 위에 올리기" 위한 단계이다.

이 구조는 계산 비용도 합리적으로 배분한다. 1단계는 코퍼스 전체(수십만 문서)에 대해 근사 최근접 탐색(ANN)을 수행하고, 2단계는 이미 걸러진 소수(예: 20개) 후보에 대해서만 고비용 모델을 적용한다.

평가 지표 정의

3.1 Recall@k

상위 k개 결과 안에 정답(ground-truth) 문서가 포함된 비율을 측정한다. 쿼리 집합 Q에 대해 각 쿼리 q에서 정답 문서가 상위 k위 안에 있으면 1, 없으면 0으로 표시할 때:

Recall@k = (1 / |Q|) × Σ_{q ∈ Q} 1[ rank(rel_q) ≤ k ]
  • rel_q: 쿼리 q에 대한 정답 문서
  • rank(·): 시스템이 부여한 순위 (1이 최상위)

Recall@k는 "정답이 목록 안에 있는가"를 묻는 이진(binary) 지표이며, 정답이 1위인지 5위인지는 구별하지 않는다. 따라서 Retrieval Coverage(커버리지)를 측정하기에 적합하다.

3.2 MRR (Mean Reciprocal Rank)

각 쿼리에서 첫 번째 정답 문서의 순위 역수(reciprocal rank)를 평균 낸 값이다.

MRR = (1 / |Q|) × Σ_{q ∈ Q} (1 / rank_q^first)
  • 정답이 1위: 기여값 = 1.0
  • 정답이 2위: 기여값 = 0.5
  • 정답이 5위: 기여값 = 0.2
  • 정답이 없음: 기여값 = 0.0

MRR은 순위에 민감하다(rank-sensitive). 동일한 Recall@5=1.0이더라도 정답이 1위에 있는 시스템과 5위에 있는 시스템은 MRR 값이 크게 다르다. 사용자 경험 관점에서 첫 번째 결과의 적합성이 중요한 경우, MRR이 더 의미 있는 지표다.

3.3 두 지표의 상보적 관계

지표 측정 대상 순위 민감도 주요 활용 맥락
Recall@k 정답의 목록 내 존재 여부 낮음 (이진) 1단계 Retrieval 커버리지 평가
MRR 정답의 실제 순위 품질 높음 (연속) 2단계 Reranking 품질 평가

Recall@k가 충분히 높은 상태에서 MRR이 낮다면, 정답 문서는 후보군에 들어오지만 순위가 뒤로 밀린다는 뜻이다. 이 상황에서 Reranker는 Recall을 희생하지 않으면서 MRR을 향상시키는 역할을 할 수 있다.

Listwise Reranking: 방법론 비교

4.1 Reranking 방식 분류

방식 입력 단위 모델 추론 횟수 컨텍스트 대표 모델
Pointwise 쿼리 + 단일 문서 k₁ 회 문서 간 상대 관계 없음 Cross-encoder (단순)
Pairwise 쿼리 + 문서 쌍 O(k₁²) 두 문서 간 비교 RankNet, LambdaMART
Listwise 쿼리 + 전체 목록 1 회 전체 후보 간 상대 관계 LLM (GPT-4o-mini 등)

4.2 LLM 기반 Listwise Reranking의 원리

LLM Listwise Reranker는 쿼리와 후보 문서 목록 전체를 하나의 프롬프트로 입력받아, 각 문서의 관련성을 목록 내 상대적 맥락을 고려하여 재정렬한다. 대형 언어 모델의 자연어 이해 능력을 활용하므로 파인튜닝 없이도 높은 성능을 낼 수 있다.

LLM Listwise의 장점
  • 단 1회 추론으로 전체 목록 재정렬 가능 (pairwise 대비 효율적)
  • 문서 간 상대적 관련성을 동시에 고려 (pointwise 대비 우수)
  • 도메인 지식 없이도 일반화 가능 (제로샷)
  • 프롬프트 수정만으로 정렬 기준 조정 가능
LLM Listwise의 단점 및 한계
  • 컨텍스트 길이 제한 — 후보 수(k₁)가 클수록 토큰 비용 증가
  • API 지연(latency) — 실시간 응답이 중요한 환경에서 병목 가능
  • Position Bias — LLM이 목록에서 앞/뒤 위치에 따라 선호를 보일 수 있음
  • 비결정성 — 동일 쿼리에 대해 결과가 달라질 수 있음

4.3 본 프로젝트의 구현

company-rag에서는 shared/retriever/ 레이어에 Reranker ABC를 정의하고, LLMReranker 구현체에서 gpt-4o-mini를 통한 listwise 프롬프트 방식을 적용했다. 1단계에서 top_k=20으로 후보를 넓힌 뒤, Reranker가 상위 5개로 압축한다. 이 설계는 Stage 1/2 경계를 명확히 하여 이후 Cross-encoder 등 다른 구현체로 교체 가능한 구조를 유지한다.

5.2 결과 해석

Recall@5가 두 시스템에서 동일하게 1.000인 것은 1단계 Dense Retrieval이 이미 충분한 커버리지(Coverage)를 제공하고 있음을 의미한다. 즉, 정답 문서는 이미 상위 5개 안에 포함되어 있었다. 이는 1단계의 역할—정답을 후보군에 올려두는 것—이 제대로 수행되고 있다는 증거다.

반면 Recall@1이 0.800 → 0.900, MRR이 0.840 → 0.950으로 향상된 것은 Reranker가 이미 후보군에 있던 정답 문서를 더 높은 순위로 끌어올렸음을 나타낸다. 이는 문제가 Retrieval Coverage가 아닌 Ranking Quality에 있었다는 사실을 명확히 드러낸다.

핵심 해석: 무엇이 개선되었는가

Recall@5 = 1.000 (변화 없음) → 정답 문서는 이미 목록 안에 있었다.
MRR 0.840 → 0.950 (+0.110) → Reranker가 정답을 순위상 더 앞으로 이동시켰다.
Recall@1 0.800 → 0.900 (+0.100) → 10개 쿼리 중 1개가 이제 1위에 정답을 얻는다.

5.3 MRR 향상의 실질적 의미

MRR 기대값 0.950은 평균적으로 사용자가 결과 목록의 1.05위 근처에서 정답 문서를 만난다는 것을 의미한다(1/0.950 ≈ 1.05). Baseline의 MRR 0.840은 1/0.840 ≈ 1.19위에 해당한다. 이 0.14 순위 차이는 소수의 질문에서 정답이 2~3위에 위치했던 사례들이 Reranking 후 1위로 올라왔음을 반영한다.

RAG 시스템에서 LLM이 컨텍스트로 주입받는 문서의 순위는 Lost in the Middle 현상과 직접 연관된다. 정답 문서가 1위(상단)에 위치할수록 최종 답변 품질이 높아지는 경향이 있으므로, MRR 향상은 단순 순위 지표 개선을 넘어 하류(downstream) 생성 품질에도 영향을 미칠 수 있다.

한계 및 후속 과제

  • 평가 셋 규모: 10개 쿼리는 통계적 유의성 확보에 불충분하다. 신뢰 구간(95% CI) 기준 ±0.16 수준의 불확실성을 고려해야 한다. 최소 100개 이상의 쿼리로 반복 측정이 필요하다.
  • Latency 측정 부재: LLMReranker는 gpt-4o-mini API 호출을 포함하므로 응답 지연이 발생한다. 품질-지연 tradeoff를 별도로 측정해야 한다.
  • Position Bias 검증: Listwise 방식에서 입력 문서 순서를 변경한 뒤 결과 일관성을 측정하는 실험(permutation test)이 필요하다.
  • 비교 대상 확장: Cross-encoder 기반 Reranker(예: ms-marco-MiniLM)와의 성능·비용 비교가 필요하다.
  • RRF(Reciprocal Rank Fusion): 동일 Phase에서 구현된 RRF Reranker와의 성능 비교를 통해 모델 없는 앙상블 방식의 효과를 평가해야 한다.

결론

본 실험은 Two-Stage Retrieval에서 각 단계가 서로 다른 문제를 해결함을 실증적으로 확인했다. 1단계 Dense Retrieval은 정답 문서를 후보군에 포함시키는 Coverage를 담당하고 (Recall@5 = 1.000), 2단계 LLM Listwise Reranker는 이미 후보군에 들어온 정답 문서를 상위 순위로 끌어올리는 Ranking Quality를 담당한다(MRR +0.110).

Reranker가 Recall@5를 바꾸지 못한 것은 실패가 아니라 설계 의도와 일치하는 결과다. Reranker의 역할은 Recall을 높이는 것이 아니라, 1단계가 올려둔 정답 문서를 더 빠르게 사용자에게 노출하는 것이기 때문이다. 이 결과는 company-rag의 현재 문서 검색 파이프라인이 각 단계의 책임을 명확히 분리하고 있음을 보여준다.
