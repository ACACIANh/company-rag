## 1. 아키텍처 & 레이어 경계

### Q1. `nodes/`가 "순수 함수"인데 async + core 호출(side-effect)?
**✅ 답변:** 여기서 "순수 함수"는 수학적 순수성(부작용 0)이 아니라 **"노드 자체가 상태를 숨겨 갖지 않는다"**는 의미로 썼습니다. 노드는 `AgentState`를 받아 부분 state dict를 반환할 뿐, 모듈 전역 상태나 자기 인스턴스 필드를 변경하지 않습니다. 부작용(DB/LLM)은 전부 **주입된 `core` 인터페이스 호출로 위임**되고, 노드는 그 의존성을 인자로만 받습니다. 그래서 테스트에서 fake `core`를 주입하면 노드는 결정론적으로 검증됩니다 — 이것이 핵심 이점입니다.
**솔직한 보강:** 용어 선택이 오해를 부르는 건 맞습니다. CLAUDE.md 표현을 "side-effect-free composition / 의존성 주입된 변환 함수"로 고치는 게 정확합니다.

### Q2. `core`의 LangGraph 불가지 규칙, 비용 대비 효용?
**✅ 답변:** 두 가지를 얻습니다. (1) `core`를 LangGraph 없이 단독 테스트·재사용 가능 — 인제스천 스크립트(`scripts/build_index.py`)는 그래프 없이 `core`만으로 동작합니다. (2) 오케스트레이션 레이어와 도메인 인프라의 **변경 이유가 분리**됩니다(LangGraph 버전업이 retriever를 건드리지 않음). 실제 오케스트레이터를 교체한 적은 없지만, 비용은 "import 금지 규칙 1줄"로 거의 0이고, 경계가 코드 리뷰에서 드리프트를 잡아주는 가드레일 역할을 합니다.
**솔직한 보강:** "구현체 교체 가능성"은 학습 프로젝트 성격상 의도적으로 남긴 부분(CLAUDE.md 규칙 5)이라고 명확히 말합니다.

### Q3. `lifespan` 조립 지점 비대화?
**✅ 답변:** 의존성 생성을 **한 곳에 응집**한 건 의도적입니다(Composition Root 패턴) — 와이어링이 흩어지는 것보다 한 파일에서 전체 그래프를 읽는 게 낫습니다. 비대화는 `core/*/factory.py`로 **생성 로직을 위임**해 `lifespan`은 "팩토리 호출 + `app.state` 할당"만 하도록 얇게 유지합니다.
**개선 방향:** 더 커지면 `factories.py` 또는 의존성 컨테이너로 분리합니다.

## 2. LangGraph 그래프 설계

### Q4. (치명적) 입력 동일한데 재시도로 다른 답을 기대?
**✅ 답변(약점 인정형):** 날카로운 지적입니다. 환각 재시도가 **입력에 변화를 주지 않으면** temperature=0에서 동일 출력이 반복됩니다. 현재는 (a) 생성 temperature가 0이 아니어서 샘플링 변동에 기대거나, (b) 재시도 시 프롬프트에 "이전 답변이 근거를 벗어났다"는 신호를 추가하는 식이어야 의미가 있습니다. **방어 논리:** `_MAX_TOTAL_RETRIES=3`은 무한 루프를 막는 안전장치이지 품질 보장 장치가 아닙니다. 제대로 하려면 재시도 분기에서 **검증 실패 사유를 프롬프트에 피드백**(self-correction)하거나, documents를 다시 좁혀 재검색해야 합니다.
**개선 방향:** generate 재시도에 "이전 답변 + 실패 이유"를 주입하는 corrective 루프로 바꾼다.

### Q5. rewrite 재시도가 같은 결과를 낳는 무한 루프?
**✅ 답변:** 종료는 보장됩니다 — `route_after_grade`가 `relevance_score≥0.5` **또는 `retry_count≥2`**에서 무조건 `generate`로 빠지므로 최대 2회 재시도 후 탈출합니다(무한 루프 불가). 다만 "같은 재작성→같은 검색"으로 재시도가 낭비될 수 있다는 점은 인정합니다.
**개선 방향:** 재시도 시 `rewrite_strategy`를 `multi_query`로 승격하거나, retry_count를 프롬프트에 넣어 다른 각도의 재작성을 유도한다.

### Q6. `0.5` 임계값과 LLM 점수 캘리브레이션?
**✅ 답변:** 0.5는 휴리스틱 초기값이며, **하드코딩이 아니라 `edges.py` 상수로 분리**해 튜닝 가능하게 했습니다. LLM 점수의 일관성 문제는 인정 — 그래서 점수를 연속값 컷오프로 신뢰하기보다 "관련/부분/무관" 같은 **이산 등급**으로 받고 임계를 등급 기준으로 잡는 게 더 안정적입니다.
**개선 방향:** `tests/eval`로 0.4~0.6 구간을 스윕해 faithfulness/recall이 최적인 지점을 데이터로 정한다(현재 eval 하니스 부채 존재).

### Q7. 질문당 LLM 5~10회 — 레이턴시/비용?
**✅ 답변:** 트레이드오프를 명시적으로 선택했습니다 — **정확도·근거성 우선** 설계입니다. 비용은 `cost_tracker`로 추적하고, 단계별로 **작은 모델로 분리**할 수 있습니다(router/grade/hallucination은 Haiku급, generate만 Opus급). 또 `route`가 단순 질문을 `tool_call`/단순 경로로 빼서 전체 그래프를 안 타게 합니다.
**개선 방향:** grade·hallucination을 비-LLM(임베딩 유사도/NLI 경량 모델)로 대체해 LLM 호출 수를 줄인다. p95는 측정해 SLO로 관리해야 한다(현재 미측정이면 인정).

### Q8. HITL이 tool_call에만, doc_search는 무확인 외부 전송?
**✅ 답변:** HITL의 목적을 **"비가역적 부작용(side-effect) 차단"**으로 잡았기 때문입니다 — 캘린더 등록·메일 발송 같은 도구는 되돌릴 수 없어 사람 확인이 필수입니다. 반면 doc_search는 읽기 전용이라 confirm 대상이 아닙니다. **데이터 유출 우려는 별개 통제 레이어**(FGA pre-filter로 권한 문서만 검색, LLM provider와의 DPA/무학습 계약)로 다룹니다.
**개선 방향:** 민감 등급 문서는 외부 LLM 전송 전 마스킹/온프레미스 모델 라우팅을 추가한다.

## 3. RAG 검색 품질

### Q9. 고정 500자 청킹이 구조를 무시?
**✅ 답변:** 고정 청킹은 **베이스라인**으로 의도한 단순 선택입니다(Karpathy 원칙: 단순함 우선). `chunker`는 ABC라 `Recursive/Markdown` 청커로 교체 가능하게 설계돼 있습니다. 50자 overlap은 경계 잘림의 컨텍스트 손실을 일부 완화합니다.
**개선 방향:** 마크다운 헤더 기준 구조 청킹 + 표/코드블록 원자성 보존으로 교체하고 eval로 효과 검증.

### Q10. NoOp reranker인데 20→5 절단 기준?
**✅ 답변:** NoOp일 때는 **retriever의 벡터 거리순 상위 5개**가 그대로 답이 됩니다. `retrieve_top_k=20`은 reranker가 **켜졌을 때**를 위한 후보 풀이며, NoOp이 기본인 건 외부 비용 없는 안전한 디폴트일 뿐 운영 권장값이 아닙니다.
**솔직한 보강:** NoOp+top_k=20 조합은 낭비가 맞으므로, NoOp일 때 retrieve_top_k를 top_k로 맞추는 최적화를 넣을 수 있습니다.

### Q11. multi_query RRF 병합인데 NoOp이면?
**✅ 답변:** RRF는 reranker 구현 중 하나(`rrf_reranker.py`)로, multi_query를 쓸 땐 RRF reranker를 함께 켜는 조합을 전제합니다. NoOp이면 분해 쿼리 결과를 단순 합집합 후 거리순으로 처리합니다.
**개선 방향:** multi_query 전략이 선택되면 reranker를 RRF로 강제 결합하고, 분해 효과를 eval A/B로 측정.

### Q12. 임베딩 차원 고정 → 교체 시 전체 재인덱싱?
**✅ 답변:** 맞습니다 — **임베딩 모델 교체는 본질적으로 재인덱싱이 필요한 작업**이며, 이는 이 시스템의 한계가 아니라 벡터 검색의 근본 속성입니다(차원·벡터 공간이 바뀌므로). `embedder` ABC는 "런타임 무중단 교체"가 아니라 "**코드 변경 없는 모델 선택 + 재빌드**"를 위한 추상화입니다.
**개선 방향:** 차원을 메타데이터에 기록하고, 모델 변경 감지 시 재인덱싱을 강제하는 가드를 둔다.

## 4. FGA 권한제어

### Q13. (치명적) 트리 상속 모델인데 검색은 정확 매칭으로 평탄화?
**✅ 답변:** 모순이 아니라 **역할 분리**입니다. 트리 상속(`can_read from parent`)은 **OpenFGA가 권한을 판정하는 규칙**이고, `ListObjects`가 그 상속을 모두 풀어 **사용자가 읽을 수 있는 폴더의 평면 목록**을 돌려줍니다. 검색의 `path = ANY()` 정확 매칭은 그 "이미 판정된 결과"에 거는 필터라 트리 의미를 무력화하지 않습니다 — 오히려 prefix 매칭을 쓰면 하위 폴더의 **선택적 차단(private)**을 표현할 수 없어 트리 모델이 깨집니다.
**확장성:** 폴더 수가 수천 개면 `path = ANY(거대배열)`이 부담인 건 맞습니다. → 폴더에 **정수 ID 부여 + `documents.folder_id IN (...)` 인덱스 조인**, 또는 사용자별 권한을 비트셋/별도 권한 테이블 조인으로 푸는 방향으로 확장합니다.

### Q14. 캐시 TTL 60초 = 권한 회수 후 최대 60초 노출?
**✅ 답변:** TTL은 성능과 신선도의 트레이드오프이고, **즉시성이 필요한 경우 `invalidate()`로 능동 무효화**합니다(권한 변경 API에서 호출). 60초는 "조회는 빈번, 권한 변경은 드묾"이라는 가정에서의 상한입니다.
**솔직한 보강:** "모든 권한 변경 경로가 invalidate를 부른다"는 코드로 강제되지 않으면 깨질 수 있습니다 → 권한 변경을 단일 서비스 경유로 모아 invalidate를 보장하고, 민감 작업은 TTL을 더 짧게(또는 캐시 우회) 합니다.

### Q15. path 문자열 의존 → 이동/리네임 시 동기화?
**✅ 답변:** 인제스천이 권한 경계인 `folder_path`를 **단일 출처(파일 시스템 경로)에서 일관되게 생성**하므로, 재인덱싱 시 path가 함께 갱신됩니다. FGA의 folder 식별자도 동일 경로 체계를 씁니다.
**솔직한 보강:** 실시간 이동/리네임 동기화는 현재 약점입니다 → 폴더를 **불변 ID로 식별**하고 path는 표시용으로만 쓰면 리네임에 강건해집니다(Q13 개선과 동일선상).

### Q16. PostgreSQL 캐시가 핫패스인데 지연/경합?
**✅ 답변:** 권한 조회는 user당 1행 PK 조회라 매우 가볍고, 같은 커넥션 풀을 쓰므로 추가 인프라(Redis)의 운영·네트워크 비용이 없습니다(ADR-0009). TTL 60초로 대부분 캐시 히트라 FGA 왕복도 줄입니다.
**개선 방향:** 부하 테스트로 풀 경합을 측정하고, 병목 시 권한 조회 전용 풀 분리 또는 프로세스 로컬 L1 캐시(짧은 TTL) 추가.

## 5. 인제스천 & 데이터 모델

### Q17. 원본 버전업 시 옛 청크 stale?
**✅ 답변(약점 인정형):** 핵심 지적입니다. `document_versions`/`originals`는 버전을 올리지만, **벡터 `documents`의 옛 청크를 지우지 않으면** 검색에 stale 청크가 남습니다. 올바른 동작은 **재인덱싱 시 해당 `document_id`의 기존 청크를 삭제 후 재삽입**(또는 version 컬럼으로 최신만 검색)하는 것입니다.
**개선 방향:** 인덱서에 "document_id 단위 upsert(기존 청크 purge)"를 추가하고, documents에 version을 넣어 `WHERE version = 최신`으로 필터.

### Q18. PDF 추출 품질(다단/표/스캔)과 실패 감지?
**✅ 답변:** 파서를 **포맷별로 격리**(ADR-0013)해 PDF 추출 로직을 교체·강화하기 쉽게 했습니다. 현재 `pdfminer` 기반 텍스트 추출은 단순 텍스트 PDF에 적합하고, 스캔/복잡 레이아웃은 한계가 있음을 인정합니다.
**개선 방향:** 추출 텍스트 길이/문자 비율로 **품질 게이트**를 두어 빈/깨진 추출을 인덱싱에서 제외하고, 스캔 PDF는 OCR 파서로 분기. 표는 마크다운 표로 변환하는 파서 추가.

### Q19. MD5 chunk_id 충돌로 덮어쓰기?
**✅ 답변:** chunk_id 해시에 **content만이 아니라 source/path + 청크 인덱스를 포함**하면 서로 다른 문서의 동일 문장이 충돌하지 않습니다. 동일 문서 내 동일 청크의 해시 일치는 오히려 **중복 제거(idempotent 재인덱싱)**에 유리합니다.
**확인 필요:** 현재 해시 입력에 path가 포함되는지 코드로 확인해 답해야 합니다(포함 안 되면 버그로 인정 + 수정).

## 6. 운영 · 확장성 · 신뢰성

### Q20. MemorySaver(dev) vs PostgresSaver(prod) 불일치?
**✅ 답변:** checkpointer를 **인자로 주입**(`build_graph(checkpointer=...)`)해 환경별로 갈아끼웁니다. 멀티 워커에서 interrupt 재개는 **공유 저장소(Postgres)가 필수**라 운영은 `AsyncPostgresSaver`를 씁니다. dev에서 MemorySaver는 단일 프로세스라 충분합니다.
**솔직한 보강:** dev/prod 동작 차이를 줄이려면 통합 테스트는 Postgres checkpointer로 돌려 HITL 재개 경로를 운영과 동일하게 검증해야 합니다.

### Q21. cost_tracker JSON 파일 동시 쓰기 race?
**✅ 답변(약점 인정형):** 멀티 워커에서 파일 append는 race·유실 위험이 있습니다. 현재는 관측/디버깅용 경량 로깅 수준입니다.
**개선 방향:** 비용 이벤트를 구조화 로그(stdout)→수집기로 보내거나 DB 테이블에 적재해 집계 정확성을 보장한다.

### Q22. chat_history 10턴 윈도우, 앞부분 손실?
**✅ 답변:** 컨텍스트 길이·비용·레이턴시를 위한 **단순한 최근성 윈도우**입니다. RAG 특성상 사실은 검색으로 보충되므로 대화 윈도우의 손실 영향이 상대적으로 작습니다.
**개선 방향:** 윈도우 + **롤링 요약**(오래된 턴을 요약해 system에 유지)으로 긴 대화의 의도 연속성을 보존.

### Q23. (치명적) ainvoke(완료 후 반환)인데 토큰 스트리밍?
**✅ 답변:** `answer_question`의 `ainvoke`는 **비스트리밍 `/chat` 경로**의 헬퍼이고, `/chat/stream`은 LangGraph의 **`astream`/`astream_events`**로 노드 진행·LLM 토큰을 이벤트로 받아 SSE로 흘립니다. 즉 단발 응답과 스트리밍은 **다른 실행 API**를 씁니다. generate 노드의 `LLMClient.stream()`이 토큰 소스입니다.
**확인 필요:** 실제 `/chat/stream` 핸들러가 astream 계열을 쓰는지 코드로 확인해 정확히 답합니다(만약 ainvoke 후 일괄 전송이면 "유사 스트리밍"임을 솔직히 인정).

## 7. 보안 · 프라이버시

### Q24. JWT HS256 + users.yaml, 비번/회전/폐기?
**✅ 답변:** 현재는 **데모/사내 PoC** 수준 인증입니다 — `config/users.yaml`은 시드용입니다. 운영 수준 답변: 비밀번호는 bcrypt/argon2 해시 저장, 시크릿은 환경변수+회전, 토큰은 **짧은 만료 + refresh + 서버측 블록리스트**로 폐기 처리해야 합니다.
**개선 방향:** 사용자 저장소를 DB로 이전하고 OIDC/SSO 연동.

### Q25. 검색 pre-filter와 다운로드 권한 검사 로직 공유?
**✅ 답변:** 둘 다 **동일한 `FGAClient`(`get_readable_folders`/권한 판정)**를 통해야 드리프트가 없습니다. 다운로드 엔드포인트도 같은 클라이언트를 의존성 주입받습니다.
**솔직한 보강:** "같은 함수"를 쓰는지 코드로 확인 — pre-filter는 `build_pg_filter`, 다운로드는 단건 폴더 권한 체크라 **경로가 다르면 공통 권한 판정 함수로 통일**해 단일 진실원천을 만든다.

### Q26. 사내 문서를 외부 LLM에 전송, 통제?
**✅ 답변:** 계약 레벨(provider와 DPA, 무학습 옵트아웃, 리전 고정)과 기술 레벨(FGA로 권한 문서만 전송, 전송 전 PII 마스킹, 감사 로그)을 병행해야 합니다. provider를 ABC로 추상화해 **온프레미스/리전 모델로 전환 가능**하게 한 것이 통제 옵션입니다.

## 8. 테스트 · 평가

### Q27. 노드 단위테스트 OK, 그래프 엣지/루프 커버리지?
**✅ 답변:** `edges.py`의 라우팅 함수들은 **순수 함수라 단위 테스트로 분기를 직접 검증**합니다(임계값 경계값 테스트). 무한 루프 방지는 `retry_count` 상한으로 보장되고, 이를 "상한 도달 시 탈출" 테스트로 못박습니다. 그래프 전체는 fake `core` 주입으로 통합 테스트합니다.
**개선 방향:** 각 조건부 분기의 모든 경로를 커버하는 시나리오 테스트 + HITL interrupt/resume를 Postgres checkpointer로 검증.

### Q28. tool_executor Mock인데 실제 도구 붙이면?
**✅ 답변:** 도구 실행을 Mock으로 둔 건 **그래프 토폴로지/HITL 흐름을 도구 구현과 분리**해 먼저 검증하기 위함입니다. 실제 도구를 붙이면 (a) 부작용·타임아웃·실패 처리(CLAUDE.md 규칙 3: retry+timeout 필수), (b) confirm 이후 도구 실패 시 사용자 재확인/롤백 경로가 필요합니다.
**개선 방향:** 도구를 `core` 인터페이스로 추상화하고, 실패를 state에 싣고 generate가 실패를 설명하도록 분기 추가.

### Q29. eval 골든셋/지표/합격 기준?
**✅ 답변:** `tests/eval/runner.py`로 회귀 점수를 보고(DoD 항목), 지표는 faithfulness(환각)·context recall/precision 중심이어야 합니다. 임계값 변경 시 eval을 돌려 **점수 하락 시 원인 명시**가 규칙입니다(CLAUDE.md DoD).
**솔직한 보강:** 현재 **eval 하니스에 선재 부채**(지표 타입·compare_reranker 미배선)가 있어 회귀 신뢰도가 제한적입니다 — 이를 먼저 갚아야 임계값 튜닝(Q6)이 데이터 기반이 됩니다.
